# Luciola 协议 v0.1

版本 0.1 · 2026-10-03

## 1. 概述

![lociola](../brand/luciola.png)

Luciola 是一个去中心化社交协议。协议由两种元素和一个角色构成：**身份**（Identity）签发 **action**（Action），action 存放于**节点**（Node），并沿关系在节点之间流通。

### 1.1 原则

1. 所有节点平等。节点的规模不影响其在协议中的地位，协议中不存在中心节点、全局索引或共享屏蔽名单。
2. 节点运营者对自己的节点负责，包括准入、拉黑、存储与带宽。
3. 内容只沿关系流通；没有关系，内容不会被推送到任何其他节点。
4. 身份属于用户，以用户自持的主密钥为根，节点无法夺取。
5. 每个 action 的权威版本位于其作者发出时所在的节点。

### 1.2 规范用语

本文中"必须"、"不得"、"应当"、"可以"的含义与 RFC 2119 中的 MUST、MUST NOT、SHOULD、MAY 相同。

## 2. 术语

| 术语 | 定义 |
| --- | --- |
| 身份 | 一个用户，由其主密钥公钥唯一确定 |
| 主密钥 | 用户自行保管的根密钥，只用于签发委托、吊销与迁移 |
| 子密钥 | 经主密钥委托、代表身份签名其他 action 的密钥 |
| 节点 | 托管身份、存储与提供 action 的服务器，以域名标识 |
| 运营者 | 节点的管理者 |
| 主节点 | 某身份当前有效委托所指向的节点 |
| 源节点 | 某个 action 的 `node` 字段所指的节点 |
| action | 由身份签名的一条记录，是协议中唯一的内容单位 |
| 关注者 | 关注了某身份的身份 |
| 待处理回复 | 已被接收、尚未被放行的外节点回复 |
| 放行 | 允许一条待处理回复显示的行为 |
| 占位 | 可见性规则下，替代显示某条内容、并指向其源节点的标记 |
| 地址 | `@handle@node` 形式的身份标识 |

## 3. 编码约定

- **数据格式**：所有 action 与接口数据均为 UTF-8 编码的 JSON。
- **规范化**：计算哈希与签名前，必须按 RFC 8785（JSON Canonicalization Scheme，JCS）对 JSON 进行规范化。
- **二进制值**：公钥、签名、哈希均以 base64url（RFC 4648 第 5 节，无填充）编码，并带算法前缀：公钥为 `ed25519:<base64url>`，哈希为 `sha256:<base64url>`，签名为 `ed25519:<base64url>`。
- **时间**：一律为 RFC 3339 格式的 UTC 时间，例如 `2026-10-03T08:00:00Z`。
- **域名**：节点以小写的完整域名标识，不含协议头与路径。
- **版本**：本文定义的版本为 `0.1`。每个 action 必须带 `luciola` 字段，其值为 `"0.1"`；HTTP 接口位于路径前缀 `/luciola/v0/` 下。

## 4. 身份与密钥

身份由主密钥确定；主密钥通过委托授权子密钥，日常 action 由子密钥签名。

### 4.1 算法

主密钥与子密钥均使用 Ed25519（RFC 8032）。

### 4.2 主密钥

- 身份标识即主密钥公钥，形如 `ed25519:<base64url>`。
- 主密钥由用户生成并自行保管。主密钥只用于签名 `delegate`、`revoke`、`migrate` 三类 action。
- 导出格式：主密钥的 32 字节种子必须能以 BIP39 助记词（24 个英文单词，以种子作为熵）导出与导入。所有节点与客户端必须支持该格式的导入。
- 主密钥丢失或泄露，身份即丢失，协议不提供恢复机制。

### 4.3 子密钥与委托

- 子密钥是一把独立的 Ed25519 密钥，经 `delegate` action 绑定到一个节点后，可代表该身份签名除 4.2 所列以外的全部 action。
- 子密钥可由节点持有并代为签名，也可由用户在自己的设备上持有。
- 子密钥不是独立身份，它签名的 action 一律归属于委托它的身份。
- 同一身份所有有效的委托必须指向同一个节点，该节点即为主节点。指向其他节点的 `delegate` 无效，除非其前已有指向该节点的 `migrate`。

### 4.4 密钥状态

- **吊销**：`revoke` 使指定子密钥失效。节点在收到 `revoke` 之后，对此后才首次收到的、由该子密钥签名的 action，必须一律拒绝，不论其 `created` 字段为何。此前已收到并保存的 action 不受影响。
- **退役**：`migrate` 使指向旧节点的全部委托退役。退役的子密钥不得再签名新的 action：节点在收到 `migrate` 之后，对此后才首次收到的、由退役子密钥签名且 `created` 晚于该 `migrate` 的 action，必须拒绝。由退役子密钥签名、`created` 早于该 `migrate` 的 action 仍然有效，以保证旧节点上的历史内容可被验证。
- 用户若不信任旧节点，可以对旧子密钥发出 `revoke`，此时适用吊销规则。

## 5. Action

action 是协议中唯一的内容单位。action 一经签发不可修改；协议不提供编辑。

### 5.1 结构

```json
{
  "luciola": "0.1",
  "id": "sha256:...",
  "type": "post",
  "author": "ed25519:...",
  "key": "ed25519:...",
  "node": "example.org",
  "created": "2026-10-03T08:00:00Z",
  "target": [],
  "content": {},
  "sig": "ed25519:..."
}
```

| 字段 | 说明 |
| --- | --- |
| `luciola` | 协议版本，固定为 `"0.1"` |
| `id` | action 的唯一标识，计算方法见 5.2 |
| `type` | action 类型，见 5.4 |
| `author` | 作者身份，即主密钥公钥 |
| `key` | 签名所用的公钥；主密钥签名时等于 `author` |
| `node` | 作者签发时所在的节点，即源节点 |
| `created` | 作者声明的创建时间，仅用于展示、排序及 4.4 的退役判断 |
| `target` | 被引用的 action id 数组，无引用时为空数组 |
| `content` | 与类型相关的内容对象，见 5.5 |
| `sig` | 对 `id` 的签名 |

所有字段都是必需的。action 不得包含上表以外的字段。

### 5.2 标识与签名

1. 取除 `id` 与 `sig` 外的全部字段，按 JCS 规范化。
2. 对规范化结果计算 SHA-256，编码为 `sha256:<base64url>`，作为 `id`。
3. 以 `key` 对应的私钥，对 `id` 字符串的 UTF-8 字节签名，编码为 `ed25519:<base64url>`，作为 `sig`。

### 5.3 验证

节点收到 action 时，必须依次验证以下各项，任何一项不通过即拒绝：

1. 字段齐全且类型合法，`luciola` 为 `"0.1"`。
2. 按 5.2 重新计算的 `id` 与 `id` 字段一致。
3. `sig` 能被 `key` 验证。
4. 若 `type` 为 `delegate`、`revoke` 或 `migrate`，`key` 必须等于 `author`；否则，`key` 必须有一条由 `author` 签发的有效委托，且依 4.4 未被吊销或退役。
5. `content` 与 `target` 符合 5.5 对该类型的规定。

### 5.4 类型

| 类型 | 签名者 | `target` | 说明 |
| --- | --- | --- | --- |
| `post` | 子密钥 | 空 | 发帖 |
| `reply` | 子密钥 | [被回复的 action] | 回复一条 post 或 reply |
| `forward` | 子密钥 | [被转发的 action] | 转发 |
| `approve` | 子密钥 | [被放行的 reply] | 放行 |
| `follow` | 子密钥 | 空 | 关注 |
| `unfollow` | 子密钥 | 空 | 取消关注 |
| `remove` | 子密钥 | 空 | 移除关注者 |
| `block` | 子密钥 | 空 | 屏蔽 |
| `unblock` | 子密钥 | 空 | 取消屏蔽 |
| `delete` | 子密钥 | [被删除的 action] | 删除自己的 action |
| `profile` | 子密钥 | 空 | 个人资料 |
| `delegate` | 主密钥 | 空 | 委托子密钥 |
| `revoke` | 主密钥 | 空 | 吊销子密钥 |
| `migrate` | 主密钥 | 空 | 迁移 |

### 5.5 内容

- `post`：`{ "text": 字符串, "media": 媒体数组, "mentions": 身份数组 }`。`text` 为纯文本，不超过 10000 个字符；`media` 不超过 4 项，格式见第 13 节；`mentions` 列出正文中提及的身份。三个字段都必须存在，可为空。
- `reply`：在 `post` 的字段之外，另含 `"root"`，值为所在讨论串根 post 的 id。
- `forward`、`approve`、`delete`：`{}`。`approve` 的签名者必须是被放行 reply 所回复对象的作者；`delete` 的签名者必须是被删除 action 的作者。
- `follow`、`unfollow`、`remove`、`block`、`unblock`：`{ "subject": 身份 }`。
- `profile`：`{ "handle": 字符串, "name": 字符串, "bio": 字符串, "avatar": 媒体或 null }`。`handle` 规则见第 12 节；`name` 不超过 64 个字符；`bio` 不超过 1000 个字符。同一身份的 profile 以 `created` 最新的一条为准。
- `delegate`：`{ "subkey": 公钥, "node": 域名 }`。
- `revoke`：`{ "subkey": 公钥 }`。
- `migrate`：`{ "node": 新节点域名 }`。

### 5.6 可见范围

协议中的 action 均为公开内容。节点可以为用户提供仅自己可见的内容，此类内容不属于 action，不得被推送，也不得出现在任何接口的返回中。

## 6. 节点

节点负责托管身份、存储 action、按规则推送与提供 action。签名验证不依赖节点，任何持有公钥者均可验证。

- **准入**：由运营者决定哪些身份可以在本节点注册或导入。
- **同节点信任**：同一节点上的身份之间，回复无需放行。
- **身份索引**：节点必须维护本节点身份的 handle 索引，供地址解析使用（第 12 节）。
- **默认执行**：对于 `delete` 与 `migrate`，节点默认按本文执行；运营者可以选择不执行，后果由运营者承担。
- **数据导出**：节点是否向用户提供其数据的打包导出，由运营者决定。
- **成本**：节点必须能接收并存储本文规定上限内的全部内容，存储与带宽由运营者承担。

## 7. 流通

双方在线时，新 action 由推送送达；完整性由向源节点拉取保证；节点离线期间缺失的内容，在其恢复后通过拉取补齐。

### 7.1 推送对象

action 签发后，由作者的主节点推送至下表所列的节点。同一节点只推送一次。

| 类型 | 推送对象 |
| --- | --- |
| `post`、`profile` | 作者关注者所在节点；`mentions` 中身份的主节点 |
| `reply` | 被回复 action 的源节点；作者关注者所在节点；`mentions` 中身份的主节点 |
| `forward` | 作者关注者所在节点；被转发 action 的源节点 |
| `approve` | 被放行 reply 的源节点；作者关注者所在节点 |
| `follow`、`unfollow`、`remove` | `subject` 的主节点 |
| `delete` | 与被删除 action 的推送对象相同 |
| `delegate`、`revoke` | 作者关注者所在节点 |
| `migrate` | 作者关注者所在节点；新节点另须将其发送至旧主节点（第 11 节） |
| `block`、`unblock` | 不推送 |

### 7.2 推送规则

- 推送通过 `POST /luciola/v0/inbox` 进行（第 14 节）。
- 每个 action 对每个目标节点只推送一次。目标节点返回 2xx 即视为送达。
- 目标节点不可达时，推送方必须直接丢弃，不得重试。
- 接收方必须按 5.3 验证每个 action，验证通过后保存。

### 7.3 屏蔽报告

`block` 只在屏蔽者所在节点生效。屏蔽发生时，屏蔽者所在节点应当向被屏蔽身份的主节点发送一份报告（`POST /luciola/v0/reports`），报告只包含被屏蔽的身份与相关 action 的 id，不得包含屏蔽者的任何信息。报告是信号，收到报告的节点是否处理，由其运营者决定。

### 7.4 拉取

- 查看某个 action、某个身份的历史、某条 post 的讨论串时，节点向相应的源节点拉取。
- 一个 action 的权威版本由其源节点提供。源节点不可达时，非关联内容无法获取。

### 7.5 离线补齐

- 节点必须记录自己最近一次在线的时间。
- 节点恢复在线后，必须对本节点身份所关注的每个身份，向其主节点请求该时间之后的 action（`since` 参数），补入本地。
- 某主节点此时不可达，则跳过，待其可达或有用户访问该身份时再补。

## 8. 回复与放行

外节点的回复默认不显示，是否显示由被回复的一方决定。

### 8.1 是否需要放行

被回复 action 的源节点收到一条 `reply` 时：

- 回复者与被回复者在同一节点，直接显示；
- 被回复者关注了回复者，直接显示；
- 其他情况，该回复成为待处理回复。

### 8.2 放行

- 放行权属于被回复 action 的作者。
- 放行针对单条回复，有两种方式：签发一条 `approve`；或被回复者对该待处理回复签发一条 `reply`，此回复本身即视为对它的放行，所有节点必须按放行处理。
- 一条回复被放行后，同一回复者此后的回复仍按 8.1 判断。

### 8.3 待处理回复

- 对同一个被回复 action，同一身份在未被放行前只能有一条待处理回复。接收节点必须拒绝第二条，返回 409。
- 某身份的第一条待处理回复，节点应当通知被回复者；在被回复者对该身份的任一待处理回复做出处理前，该身份的后续待处理回复不再通知。
- 待处理回复不过期，由节点一直保存，直到被放行、被屏蔽清除或被其作者删除。

### 8.4 屏蔽

- 被回复者屏蔽某身份后，其节点必须丢弃该身份的全部待处理回复，并拒绝该身份此后的回复。
- 节点按 7.3 发送屏蔽报告。

### 8.5 讨论串中的放行

讨论串中，每条回复由其被回复者在自己所在的节点上放行。例如：a 发帖，b 的回复被放行，c 回复 b，则 c 的回复由 b 决定是否放行。

## 9. 可见性

显示什么，取决于观看的入口。本节规定节点向用户展示内容的规则。

### 9.1 在本节点观看

用户在自己的节点上观看讨论串、转发或个人主页时：

1. 用户所关注身份的 action，直接显示。
2. 用户未关注、但已被任一身份放行的 action，显示为占位。占位必须指向该 action 的源节点，用户可前往查看。
3. 未被任何身份放行的待处理回复，不显示，也不显示占位。
4. 同节点身份的 action 直接显示。

### 9.2 从其他节点进入

用户通过某节点的链接进入时，看到的是该节点的视图，以该节点上的放行为准。

### 9.3 已删除的根

讨论串的根 post 被删除后，其下的回复保留在各自的源节点上，根的位置显示为"原帖已删除"。

## 10. 缓存与删除

### 10.1 缓存

节点必须保存与本节点身份关联的其他节点的 action 及其媒体，包括：

- 本节点身份所关注身份的 action；
- 本节点身份回复、转发或放行过的 action；
- 本节点身份参与的讨论串中的 action。

缓存的 action 保留原始签名，任何节点均可验证。源节点不可达时，节点必须继续以缓存展示这些内容。非关联内容不缓存。

### 10.2 删除

- 作者可以签发 `delete` 删除自己的 action，`delete` 本身不可被删除。
- 收到 `delete` 的节点默认删除被引用的 action 及其独有的媒体；运营者可以选择不执行。
- 被删除 action 的源节点对其 id 必须返回 410。
- 被删除 post 下的回复不随之删除，适用 9.3。

## 11. 迁移

迁移转移身份，不转移历史内容与关系。

### 11.1 流程

1. 用户在新节点导入主密钥（4.2 的 BIP39 格式），并在新节点取得 handle。
2. 用户以主密钥签发 `migrate`（`node` 为新节点），再签发指向新节点的 `delegate`，并以新子密钥签发新的 `profile`。
3. 新节点将 `migrate` 发送至旧主节点的 inbox，并按 7.1 推送。
4. 旧主节点收到 `migrate` 后，默认将其推送给该身份的关注者所在节点；运营者可以选择不推送。
5. 关注者所在节点收到 `migrate` 后，必须向关注者展示迁移通知，且不得自动转移关注关系。关注者是否关注新地址，由其自行签发 `follow` 决定。

### 11.2 迁移的范围

- 随身份转移：主密钥、handle（在新节点重新取得）、个人资料。
- 不转移：已有 action、关注者列表、关注列表。已有 action 保留在旧节点，依 4.4 仍可被验证。
- handle 在新节点已被占用时，用户必须另选 handle 或另选节点。
- 协议不要求旧节点指向新节点。旧节点对该身份旧地址的解析返回 410，不返回新地址。

## 12. 地址解析

地址的形式为 `@handle@node`。协议不提供按名字或内容的搜索；找到一个身份的方式是取得其地址。

### 12.1 handle

- 由小写字母 a–z、数字 0–9 与下划线组成，长度 1 至 30。
- 在同一节点内唯一，先到先得。

### 12.2 解析

```
GET https://{node}/.well-known/luciola?handle={handle}
```

返回：

```json
{ "author": "ed25519:...", "handle": "...", "node": "..." }
```

- 解析方必须获取该身份最新的 `profile` 并核对：`profile` 的 `handle` 与 `node` 必须与返回值一致，否则视为解析失败。
- handle 不存在返回 404；身份已迁出返回 410。

### 12.3 在本节点访问

用户在自己的节点输入地址，由本节点完成解析，并拉取对方的 profile 与 action 在本节点展示。关注、回复等操作均在本节点完成。

## 13. 媒体

媒体不嵌入 action，由 action 以哈希引用；哈希随 action 一同被签名，任何副本都可校验。

### 13.1 引用格式

```json
{ "hash": "sha256:...", "type": "image/webp", "size": 345678, "alt": "图片描述" }
```

- `hash`：媒体文件原始字节的 SHA-256。
- `type`：媒体类型，取值见 13.2。
- `size`：字节数。
- `alt`：替代文字，可为空字符串，不超过 1000 个字符。

### 13.2 格式与上限

| 类别 | 允许的类型 | 单个文件上限 |
| --- | --- | --- |
| 图片 | `image/jpeg`、`image/png`、`image/webp`、`image/gif` | 10 MB |
| 视频 | `video/mp4`（H.264 视频、AAC 音频） | 100 MB |

每个 action 最多引用 4 个媒体。1 MB 为 1,048,576 字节。

### 13.3 存放与获取

- 媒体原件由 action 的源节点提供，路径为 `GET /luciola/v0/media/{hash}`。
- 关联节点按 10.1 保存副本。
- 获取方必须校验文件的哈希、类型与大小与引用一致，不一致即丢弃。

## 14. HTTP 接口

节点之间仅通过 HTTPS 通信，请求与响应体均为 JSON（媒体除外）。节点之间不做传输层认证，可信性完全来自 action 的签名。

### 14.1 通用规则

- 路径参数中的 id、身份与哈希使用带前缀的完整字符串，例如 `/luciola/v0/actions/sha256:...`。
- 列表接口使用游标分页：参数 `limit` 默认 50，最大 100；参数 `cursor` 取自上一页响应的 `next`；`next` 为 `null` 表示没有下一页。
- 节点可以限制请求频率，超出时返回 429。

### 14.2 接口列表

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/luciola/v0/inbox` | 接收推送 |
| GET | `/luciola/v0/actions/{id}` | 获取单个 action |
| GET | `/luciola/v0/actions/{id}/replies` | 获取某 action 的回复索引 |
| GET | `/luciola/v0/identities/{author}/actions` | 获取某身份在本节点签发的 action |
| GET | `/luciola/v0/identities/{author}/keys` | 获取某身份的 `delegate`、`revoke`、`migrate` |
| GET | `/luciola/v0/identities/{author}/profile` | 获取某身份最新的 `profile` |
| POST | `/luciola/v0/reports` | 接收屏蔽报告 |
| GET | `/luciola/v0/media/{hash}` | 获取媒体文件 |
| GET | `/.well-known/luciola?handle={handle}` | 地址解析（第 12 节） |

### 14.3 接收推送

请求：`{ "actions": [action, ...] }`，一次最多 100 个。

响应 200：`{ "results": [{ "id": "...", "code": 200 }, ...] }`，逐个给出结果，`code` 取值为 200（已接收）、400（验证失败）、409（违反 8.3 的限制或已被屏蔽）、413（超出上限）。

### 14.4 获取 action

- `GET /luciola/v0/actions/{id}`：返回 action 本身；不存在返回 404，已删除返回 410。
- `GET /luciola/v0/actions/{id}/replies`：返回 `{ "replies": [{ "id": "...", "node": "..." }], "next": ... }`，只包含按本节点规则可显示的回复，不包含待处理回复。
- `GET /luciola/v0/identities/{author}/actions?since={time}`：返回 `{ "actions": [...], "next": ... }`，包含该身份在本节点签发、本节点保存时间晚于 `since` 的 action，按保存时间升序；不包含 `block` 与 `unblock`。
- `GET /luciola/v0/identities/{author}/keys`：返回 `{ "actions": [...] }`，按 `created` 升序。
- `GET /luciola/v0/identities/{author}/profile`：返回最新的 `profile` action；身份不在本节点返回 404，已迁出返回 410。

### 14.5 屏蔽报告

请求：`{ "about": 身份, "actions": [action id, ...] }`。成功返回 202。

### 14.6 媒体

`GET /luciola/v0/media/{hash}` 返回文件原始字节，`Content-Type` 为引用中的类型。

### 14.7 状态码

| 状态码 | 含义 |
| --- | --- |
| 200 | 成功 |
| 202 | 已接收报告 |
| 400 | 请求格式或签名无效 |
| 404 | 不存在 |
| 409 | 违反待处理回复的限制，或已被屏蔽 |
| 410 | 已删除或已迁出 |
| 413 | 超出大小上限 |
| 429 | 请求过多 |

## 15. 协议范围

本协议不定义以下功能，实现者不得以扩展 action 类型或字段的方式在节点之间提供它们：

- 编辑已签发的 action；
- 点赞或任何计数类反馈；
- 公开与仅自己可见以外的可见范围；
- 按名字或内容的搜索，以及任何全局索引；
- 节点之间共享的屏蔽名单；
- 旧节点对新节点的指向或转发。
